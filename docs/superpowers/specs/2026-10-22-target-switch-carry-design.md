# PR 대상이 바뀌어도 확인한 것은 확인함으로 — 설계

2026-10-22 · 로컬 폴더 모드 전용

## 왜

리뷰 도중 PR 대상 브랜치를 바꾸는 일이 있다(실측: `integration` → `test`). 새 대상 기준 diff 에는 이전 대상에 이미 있던 변경, 대개 남의 통합 작업이 끼어든다.

지금 로직은 merge-base 가 바뀌어도 확인한 변경 블록을 이어받는다. 하지만 파일 상태(수정 ↔ 새 파일)가 바뀌면 이어받기를 포기한다.

실측: 통합 브랜치에서 더 오래된 대상으로 전환했고, 이전 대상 기준으로 전부 확인했다고 가정했다.
- 이전 diff 232개 파일 중 92개만 확인함으로 남았다.
- 140개는 상태가 '수정'에서 '새 파일'로 바뀌어 '확인 후 바뀜'으로 떨어졌다. 예를 들어 이전 대상 기준으로는 내가 1줄 고친 파일이, 새 대상 기준으로는 42줄짜리 새 파일이 된다.
- 이전 diff 에 없던 3740개 파일은 '안 봄'이었다.

사용자가 원하는 것은 대상을 바꿔도 **이전 대상과 같은 줄은 확인함**으로 치는 것이다. 이전 대상에 비해 달라진 것 중 아직 안 본 것만 남긴다. 이전 대상에 이미 있던 내 줄도 확인함으로 친다(사용자 결정).

## 목표

- 이전 대상 기준으로 확인한 리뷰를, 그보다 **뒤처진 대상**으로 바꿔 열었을 때 다음 둘을 확인함으로 만든다.
  - 이전 대상과 내용이 같은 파일.
  - 이전 대상 기준으로 확인한 그대로인 파일.
- 이전 대상 기준으로 확인한 뒤 내가 더 고친 파일은 지금 로직대로 '확인 후 바뀜'이다.

## 비목표

- GitHub 모드.
- 새 대상이 이전 대상보다 앞서 있거나 갈라진 경우. 이때는 지금 로직 그대로다(아래 '켜는 조건'). (2026-11-01: 끝의 '결과 파일이 같은 파일' 규칙이 이 방향도 일부 덮는다.)
- 배지 같은 별도 표시. 이어받은 파일은 평범한 '확인함'이다(내 판단).

## 반목표 (돌아가도 실패인 것)

- **새 대상 쪽에서 온 변경을 확인함으로 덮는 것.** 새 대상이 고친 줄을 내 브랜치가 옛 내용으로 되돌린 경우가 여기에 해당하고, 이런 줄은 반드시 남아야 한다.
- **체크를 푼 것을 다시 확인함으로 만드는 것.**
- 처음 열 때 목록이 뜬 다음 상태가 뒤늦게 바뀌는 것. 읽던 파일이 갑자기 접히면 안 된다.
- 판정에 필요한 git 작업이 실패했는데 무언가를 확인함으로 바꾸는 것. 실패하면 지금 동작 그대로 간다.

## 켜는 조건 (이름이 아니라 조상 관계)

지금 merge-base 를 `N`, 지금 리뷰 파일들의 기록 중 `viewed: true` 이고 `base !== N` 인 기록의 base 를 `P` 라 한다.
- `N` 이 `P` 의 **진짜 조상**일 때만 그 `P` 로 이어받기를 한다. 판정은 `mergeBase(N, P) === N && N !== P` 다.
- 이때 `N..P` 는 전부 이전 대상 쪽 역사다. 그래서 head 의 파일이 `P` 와 같은데 `N` 과 다르다면, 그 차이는 이전 대상이 만든 것이다.
- 같은 대상이 앞으로 나가 merge-base 가 움직인 경우에는 `N` 이 `P` 의 후손이라 켜지지 않는다. A→B→A 처럼 되돌아갈 때도, 갈라진 대상이면 켜지지 않는다.
- 이름으로 판단하지 않으므로 기록에 대상 이름을 남기지 않는다. 기록 형식에는 선택 필드 `prev` 하나만 둔다(아래 '왕복').
- 조건을 만족하는 `P` 가 여럿이면 기록 수가 많은 순으로 최대 3개를 쓴다(내 판단). 조상 검사를 먼저 하고 통과한 것 중에서 3개를 고른다(검사는 기록 수 순으로 최대 10개 base 까지) — 조상이 아닌 base 가 기록이 가장 많아도 유효한 `P` 를 밀어내지 않는다.

## 판정 (P 마다)

1. `P..head` 의 diff 를 지금 스냅숏과 같은 명령(raw + patch)으로 한 번 뜬다. 이것을 P-diff 라 한다.
2. 지금 diff 의 파일마다 아래를 본다. 이미 지금 로직으로 확인함이거나 남의 파일 표시가 붙은 파일은 건너뛴다.
   - **건드리지 않는 파일**
     - 이 파일의 기록이 `viewed: false` 다(체크를 푼 것이 이긴다).
     - 기록의 `base === N` 이다(지금 대상에서 내린 판단이 이긴다).
   - **(a) 이전 대상과 같음.** 경로가 P-diff 의 어떤 항목에도 없다. 이름 변경의 원래 경로와 새 경로를 둘 다 본다. 이 경우 확인함이다.
   - **(b) 이전 대상에서 확인한 그대로.** 기록이 `viewed: true` 이고 `base === P` 이며, P-diff 쪽 이 파일의 지문이 `record.fp` 와 같다. 이 경우 확인함이다.
   - 그 밖은 지금 로직 그대로다.
3. 확인함이 된 파일은 **보통 확인 기록으로 남긴다.** 지금 스냅숏 기준 `markRecord(item, head, true)` 이고, base 는 `N` 이다.
   - 그 뒤로는 평범한 확인함이라 체크 풀기, 새 커밋, 다음 열기가 모두 지금 로직대로 동작한다.
   - 기록을 쓰는 것은 처음 이어받을 때 한 번뿐이다.
   - 기록에는 이름이 아니라 지문, 서명, SHA 만 들어간다(기존과 같다).
   - **(b) 로 이어받은 기록만** 선택 필드 `prev: { base, fp }` 를 갖는다. 값은 덮어쓰기 전 기록의 `base`(= P)와 `fp` 다. (a) 로 이어받은 기록은 P-diff 에 없는 파일이라 `prev` 가 없다. 사용자가 직접 토글한 기록(`markRecord` 일반 경로)은 `prev` 를 이어 가지 않는다.
   - 읽을 때(gist·기기 파일) `prev.base` 가 40/64자 hex OID 가 아니거나 `prev.fp` 가 sha256 hex(64자)가 아니면 `prev` 만 버리고 나머지 기록은 그대로 쓴다.

## 왕복

- 앞선 대상 P 에서 확인 → 뒤처진 N 으로 열어 (b) 이어받기 → 다시 P 로 열면, 이 기록(base N)이 P 의 지문과 달라 '바뀜'으로 보이던 문제가 있었다.
- `buildReview`: `viewed` 이고 `prev` 가 있으며 `snap.mergeBase === prev.base` 이고 `prev.fp` 가 지금 지문과 같으면 확인함이다. `record.fp === fp` 검사 바로 다음에 보고, 체크 해제(`viewed: false`)·남의 파일 표시가 이기는 순서는 그대로다.

## 타이밍

- 기록은 로드한 뒤에야 안다. gist 모드는 스냅숏 뒤에 기록을 읽는다. 그래서 판정은 기록과 스냅숏이 둘 다 있는 리뷰 계산 단계에서 한다.
- 켜는 조건을 만족하는 `P` 가 있으면 판정과 기록 쓰기가 끝날 때까지 리뷰를 보여 주지 않는다. 그동안 로딩을 표시한다. 실측 규모(4천 파일)에서 약 1초다.
- 5초 안에 안 끝나면 이 기능 없이 보여 준다. 늦게 온 결과는 버린다(내 판단). 다음 열기 때 다시 시도한다.
- 같은 `(repo, P, head)` 에 대해서는 세션 동안 다시 계산하지 않는다.
- 확인 기록을 쓸 때는 화면에 떠 있는 리뷰의 스냅숏(head·base)을 쓴다. 지금 `toggle` 은 새로 받는 스냅숏의 head 를 쓴다. 이것도 화면 스냅숏으로 맞춘다.

## git 접근

- 기존 `mergeBase`, `rawDiff`, `patchDiff` op 를 SHA 인자로 그대로 쓴다. 새 데스크톱 op 는 없다.

## 실패할 때

- 다음 경우에는 그 `P` 를 건너뛰고 지금 동작 그대로 간다.
  - `P` 가 레포에 없다.
  - 조상 판정이 실패한다.
  - diff 가 실패하거나 섹션 수가 안 맞는다.

## 빌더에게 맡기는 것

- 판정 함수를 core 의 어디에 둘지. 순수 함수로 두고, 입력은 지금 리뷰, P 별 파일 목록과 지문, 조상 여부로 한다.
- `useReview` 쪽 배선, 로딩 표시 모양.
- 테스트
  - core 단위:
    - 조상일 때 (a)·(b) 둘 다.
    - 조상이 아닐 때 아무것도 안 함.
    - 같은 대상의 base 전진에서 아무것도 안 함.
    - `viewed: false` 우선, `base === N` 기록 우선.
    - 이름 변경 원래 경로, 남의 파일 건너뜀, 여러 `P`.
  - 웹 E2E:
    - 모의 git 으로 전환 뒤 확인함, 진행률, 기록이 쓰였는지.
    - 체크 풀기가 유지되는지.
    - 실패와 5초 초과 때 지금 동작인지.
  - 데스크톱 실레포 E2E 1개: 앞선 대상 A 와 뒤처진 대상 B 를 만들어 전환.

## 결과 파일이 같은 파일 (2026-11-01 추가)

실제 브랜치에서 대상을 앞선 쪽으로 옮기면(real → test) 70개 중 7개가 '확인 후 바뀜'이 됐다. 7개 모두 결과 파일이 확인 때와 같았고, 4개는 지금 변경이 전부 그때 본 변경이었다. 나머지 3개는 처음 보는 줄(2~3줄)이 실제로 있다.

- 규칙(`sameResultCarry`, `carry.ts`): 후보는 확인한 기록의 blob 이 지금과 같고 base 가 다른 파일. 그 base 의 diff 를 다시 만들어 지문이 기록과 같을 때만 그때 본 diff 로 친다. 이전 경로·결과 mode 가 같고, 지금 diff 의 mode 변경은 그때도 있어야 하며, 지금 변경이 전부 그때 본 변경이어야 한다.
- 변경을 맞대는 좌표는 결과 파일 줄 번호다. 결과 파일이 같아서 두 diff 가 같은 좌표를 쓴다. 추가 줄은 같은 번호, 지운 줄은 그때 그 글자를 지운 블록이 결과 파일에서 차지한 구간 안. 구간인 이유: 대상이 블록 일부를 이미 가지면 지운 줄의 자리가 그 안에서 밀린다(실측 3건). 글자만 맞대는 초안은 codex 레드팀이 깼다 — 다른 함수에서 같은 글자를 지운 것이 숨는다.
- 위 반목표('새 대상이 고친 줄을 되돌린 경우')는 그대로 남는다: 그 줄은 그때 문맥이었으니 지금 추가 줄이 그때 본 추가가 아니다.
- 조상 관계는 안 본다. 근거가 결과 파일이 같다는 것이라서다. 후보가 많은 옛 base 순으로 최대 3개만 읽고, 못 읽거나 마감을 넘기면 그 파일은 지금 동작 그대로 간다.
- 이어받기 단계를 나눠 돌린다(`makeCarry` 가 단계 목록을 준다, `useReview` 가 단계마다 남은 마감으로 돌고 그때그때 쓴다). 이 단계의 시간 초과가 앞 단계 결과를 잃지 않게.
- 처음 보는 줄이 있으면 그 줄을 알려 준다(`newLines`, 저장 안 함). 그 줄이 든 덩어리만 보이고 나머지 변경은 흐리다. 재는 때의 지문이 지금과 같을 때만 쓴다 — 새 커밋으로 diff 가 바뀌면 줄 번호가 안 맞아 블록 표시로 돌아간다.
- 다른 브랜치 기록에도 같은 규칙을 쓴다(`otherBranchCarry`, 셋째 단계). 브랜치 쌍·대상 쌍 216개에서 결과 파일만 같은 파일 108개 중 38개가 전부 본 변경이었다. `2026-10-19` 설계와 README 의 '블록을 전부 봤어도 diff 가 다르면 확인함이 아니다'는 그대로다 — 그 이유(서명에 위치가 없다)를 이 규칙은 결과 파일 줄 번호로 풀기 때문이고, 결과 파일이 다르면 지금도 적용되지 않는다.
  - 이 브랜치에 기록이 아예 없는 파일만. 여기서 체크를 푼 기록이 있으면 그것이 이긴다.
  - 결과 파일이 같은 기록 중 가장 최근 것이 확인일 때만. 결과 파일이 다른 기록의 체크 풀기는 이 내용에 대한 판단이 아니라 보지 않는다. diff 까지 같은 기록은 앞 단계(`branchMatches`)가 먼저 쓴다 — 결과 파일만 같은 기록을 나중에 풀어도 그 파일은 그 diff 를 본 것이라 그대로 둔다.
  - `branchMatches` 안에서 git 을 읽지 않는다. 느린 git 이 같은 마감의 diff 일치 결과까지 잃게 하지 않으려고 별도 단계로 뺐다. 그래서 새 커밋으로 처음 나타난 파일은 이 규칙을 안 탄다(다시 열면 찾는다).
- 줄 번호까지 맞아도 숨는 것: 그때 지운 블록의 구간 안에서 대상 쪽의 같은 글자 줄을 지우는 경우. 같은 교체 구간이라 받아들인다.

## 사람이 본 diff (2026-11-02 추가)

실제 git 반례 검증에서 이어받아 다시 쓴 기록이 '사람이 본 diff'로 쓰이는 결함이 나왔다. p 기준으로 체크 → 뒤처진 n 으로 이어받기(여기까지는 설계대로) → 옆 대상 q 로 열면, n 의 diff 에만 있던 남의 변경과 본 적 없는 파일이 확인함이 됐다. `via:'target'` 기록의 지문·블록은 새 대상의 diff 다.

- `seenBasis`: 사람이 실제로 본 diff. `via:'target'` 은 `prev`, 그 밖은 기록 자신(`via:'branch'` 는 사람이 본 diff 와 같거나 부분집합). `prev` 는 항상 사람이 본 diff 를 가리키고 대상을 몇 번 옮겨도 덮지 않는다.
- `via:'target'` 기록은 자기 base·`prev` 복귀에서만 그 자체로 확인함이다. 그 밖의 대상에서는 지문이 같아도 확인함이 아니고 블록 판정도 안 한다. 사람이 본 근거가 있으면 '확인 후 바뀜'(이어받기 단계가 맞댄다), 없으면 '안 봄'.
- 뒤처진 대상으로 이어가는 동안은 그대로 이어받는다(`targetCarry`, 사용자 결정).
- 다른 브랜치: `branchMatches` 는 `via:'target'` 기록을 안 쓴다. `otherBranchCarry` 는 사람이 본 diff 와 맞댄다.

같은 검증에서 나온 다른 것들:
- 결과 파일이 같으면 블록으로 확인함이 된 파일도 첫 화면 전에 줄 번호로 맞댄다. 서명에는 자리가 없어 앞뒤 줄이 같은 다른 함수의 변경이 맞는다. 처음 보는 줄이 있으면 '확인 후 바뀜'으로 내린다. 새 커밋으로 base 가 또 움직인 스냅숏에는 안 돌린다 — 표시된 파일이 뒤집힌다(한계).
- 처음 보는 mode 변경: 기록에 `oldMode` 를 남긴다. base 가 같으면 왼쪽 트리가 같으니 비교하지 않는다. 옛 기록은 그때의 diff 를 다시 만들어 맞댄다. 지문은 안 바꾼다(기록이 전부 무효가 된다).
- base 가 같은데 blob 이 다르면 지문이 같아도 확인함이 아니다. UTF-8 이 아닌 바이트는 같은 글자로 뭉개져 patch 가 같아진다.
- 손으로 푼 기록은 남 표시를 이긴다. 다시 체크하면 평소처럼 남의 파일로 돌아간다.

수정 전 앱이 쓴 `via:'branch'` 기록에는 이어받은 기록에서 복사된 것이 섞여 있을 수 있다. 저장된 값으로는 못 가른다.
