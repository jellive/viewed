# 남의 커밋 흐리게 — 설계

2026-10-21 · 로컬 폴더 모드 전용

## 왜

통합 브랜치를 머지해 들어온 기능 브랜치(실측: 실제 업무 레포의 한 기능 브랜치)는 diff 의 대부분이 남의 커밋이다.
변경 파일 3945개 중 3746개가 남의 커밋만 닿은 파일이었다(파일-커밋 기준 남 4054, 나 306).
PR 전에 내 변경을 파일 하나씩 보려는 사람에게 그 3746개는 소음이다. 지우면 안 되고(남의 변경도 PR 에 실린다) 비켜만 있으면 된다.

## 목표

- 남의 커밋만 닿은 파일은 '확인함'처럼 **접혀 있고 진행률에서 확인한 것으로 센다**(사용자 결정).
- 나와 남이 섞인 파일은 펼친 diff 에서 **남이 쓴 줄을 다른 바탕색**으로 보인다.
- 항상 켜져 있다 — 토글 없음(사용자 결정).

## 비목표

- GitHub 모드(로컬 git 이 없다). GitHub 모드 화면은 지금 그대로.
- 남의 줄을 숨기거나 diff 에서 빼기. 언제든 펼쳐 읽을 수 있어야 한다.
- 삭제 줄(`-`)의 작성자 판정 — 누가 지웠는지는 blame 으로 바로 안 나온다. 삭제 줄은 지금 색 그대로.

## 반목표 (돌아가도 실패인 것)

- **내가 쓴 줄이 남의 것으로 접혀 숨는 것.** 판정이 애매하면 항상 '내 것'(지금과 같은 표시)으로 기운다.
- 남의 줄이 읽기 어려워지는 것 — 투명도로 흐리지 않는다(기존 `.ln.seen { opacity:.5 }` 와 다르다).
- 파일 목록이 늦게 뜨는 것 — 3945파일에서 목록 지연이 체감되면 실패.

## '나'

- 기본: 열린 레포의 `git config user.name` 과 `user.email`.
- 설정 화면에 **추가 이름/이메일 목록**(한 줄에 하나). 실측한 레포에는 같은 사람이 이름 두 개로 커밋해 있었다.
- 커밋 작성자(author)의 이름 **또는** 이메일이 이 집합에 있으면 내 커밋. 비교는 대소문자 무시·앞뒤 공백 제거. (내 판단)
- 집합이 비면(git 설정도 추가 목록도 없음) 기능이 꺼진 것과 같다 — 전부 내 것.

## 파일 단위 판정 (목록)

`mergeBase..head` 범위에서:

1. 머지가 아닌 커밋: `git log --no-merges -M --format=<작성자 이름·이메일> --name-only` → 파일마다 작성자 집합.
2. 머지 커밋: `git log --merges --cc --format=… --name-only` → 충돌 해결로 머지 커밋 자체가 내용을 바꾼 파일과 그 작성자. 1 의 집합에 더한다.
3. 이름이 바뀐 파일(스냅숏 `previousPath` 가 있음)은 옛 경로의 작성자 집합도 합친다 — 내가 옛 경로에서 고친 뒤 남이 옮겨도 내 파일로 남게. 이름이 여러 번 바뀐 사슬은 따라가지 않는다(내 판단 — 한계로 둔다). 데스크톱 ops 픽스처에 이 경우를 넣는다.
4. 작성자 표기는 `.mailmap` 을 **적용한** 값으로 통일한다 — log 는 `%aN`/`%aE`, blame porcelain 은 기본이 적용이다(빌더가 픽스처로 둘이 같은지 확인). 목록과 줄 판정이 어긋나지 않게(내 판단).
5. 파일의 작성자 집합이 비어 있지 않고 '나'와 겹치지 않으면 **남의 파일**. 나머지는 전부 내 파일(집합이 빈 파일 포함 — 실측 12개, 이름 변경 등).

실측(위 브랜치, 2026-10-21): 1+2 로 남의 파일 3746개, 0.08초. 정답(남의 파일마다 `git blame mb..head` 로 내 줄이 하나라도 있나)과 대조해 **오분류 0**.
2 를 빼면 3개가 틀린다(내가 머지 충돌을 풀며 고친 파일) — 2 는 필수다. 전 파일 blame 은 50~58초라 목록 판정에 못 쓴다.

## 줄 단위 판정 (펼친 diff)

- 파일을 펼칠 때 그 파일만 `git blame --porcelain mergeBase..head -- <path>` (파일당 평균 약 15ms 실측). 결과를 head 줄 번호 → 작성자로 들고 있는다.
- 경계 커밋(`boundary`, mergeBase 이전 줄)은 남의 것이 아니다 — 그 줄은 diff 의 문맥 줄일 뿐이다. 칠하는 대상은 **추가 줄(`+`)만**.
- 추가 줄의 작성자가 '나'가 아니면 남의 줄 표시. blame 이 실패하거나 아직 안 왔으면 표시 없음(반목표: 내 것으로 기운다).
- 남의 파일도 펼치면 같은 방식으로 칠한다(전부 칠해질 것이다).

## 보이는 방식 (시안 A 선택)

- 남의 줄: 옅은 회청색 바탕(라이트 시안 `#eef2f8`, 글자 `#3d4b5c`), 글자는 진하게. 다크 테마가 있으면 같은 톤의 어두운 짝을 만든다(색은 빌더 몫).
- 남의 파일 머리: 상태 배지 자리에 작성자 배지 — 예 `alice` / 여러 명이면 `alice 외 1`(배지 문구는 i18n). 배지 바탕은 같은 회청 톤.
- 남의 파일은 기본 접힘. 머리를 눌러 펼치는 건 지금과 같다.
- '확인함' 체크박스: 체크된 채로 비활성, 툴팁/라벨로 "남의 변경이라 자동 확인"(내 판단 — 남의 파일엔 기록을 쓰지 않는다).
- '안 본 것만' 필터에서 남의 파일은 빠진다(확인함과 같은 취급).

## 진행률·기록

- 남의 파일은 `ReviewItem.state = 'viewed'` 로 세고, 이를 표시하는 필드(예 `others: string[]` 작성자 목록)를 단다. **ViewRecord 는 쓰지 않는다** — 다음에 내가 그 파일을 고치면 저절로 내 파일이 되어 '안 봄'으로 돌아온다.
- 내가 예전에 직접 '확인함'으로 기록한 파일이 지금 남의 파일이면 남의 파일 표시가 이긴다(어차피 둘 다 확인함).
- 완료 판정(`complete`)은 지금 식 그대로 — 남의 파일도 viewed 로 센다.

## git 접근 (데스크톱)

- 렌더러가 부를 수 있는 `ops` 에 두 가지를 더한다: 범위 작성자 목록(1+2), 파일 blame(줄 → 작성자). 인자 검증은 기존 규칙 그대로(커밋은 `oid`, 경로는 `checkPath`), `--no-textconv`·`--no-ext-diff`·`--no-show-signature`, 마감 있음.
- `user.name`/`user.email` 은 `repo:info` 에 더한다.
- 반환은 이름·이메일·파일 경로 문자열뿐. viewed 레포는 공개라 테스트 픽스처에 실제 이름·이메일을 넣지 않는다.

## 실패할 때

- 작성자 목록 명령이 실패하면 기능이 없는 것처럼(전부 내 파일) 뜨고 조용히 넘어간다. 목록 로딩을 막지 않는다.
- 기존 '확인 후 바뀐 곳'(SinceViewed) 화면에서도 추가 줄 색은 같은 규칙으로 칠한다(빌더가 그 뷰의 줄 좌표를 head 번호로 맞춘다).

## 빌더에게 맡기는 것

- 다크 테마 색 값, 배지 문구, 설정 화면의 추가 이름 입력 모양.
- 작성자 목록을 스냅숏 로딩과 병렬로 받을지, 목록 뒤에 덧입힐지(반목표: 목록 지연 금지).
- 테스트: core 판정(작성자 집합·'나' 매칭·빈 집합), 데스크톱 ops(가짜 레포에 두 작성자 + 머지 충돌 해결 커밋), 웹 E2E(접힘·진행률·줄 바탕).
