# viewed — "확인 후 바뀐 곳"을 내 변경 블록 기준으로 (설계)

작성 2026-10-19. 설계 레인: agy 블라인드(gemini-3.8-flash-high, 블록 서명안을 독립 제안) · codex 레드팀(gpt-6.1-sol/medium, REVISE) · cursor 실물 대조(composer-2.5). 방식은 Jell 결정(2026-10-19, 블록 서명).
초안(덩어리 applyPatch 안)은 기각 — 아래 §8.

## 1. 왜

Jell 증언(2026-10-19): "확인 후 바뀐 줄"에 **전체 diff 가 나왔다**, **내가 안 한 변경이 섞였다**. 재현(임시 git 레포, 앱과 같은 계산):

| 경우 | 지금 |
|---|---|
| S1 dev 가 내 줄 3줄 안쪽을 고치고 리베이스 | 지문(base...head patch 전문)이 문맥 때문에 바뀌어 `확인 후 바뀜`, 보이는 줄은 dev 줄뿐 |
| S2 내 커밋 일부가 dev 에 스쿼시로 들어가고 리베이스 | blob 같음 → "내용 같음" 안내 + 이미 본 전체 diff |
| S3 dev 를 머지하고 내가 또 고침 | `확인 당시 blob → 지금 blob` 이라 dev 줄과 내 새 줄이 섞임 |

원인: 판정은 문맥까지 든 patch 해시, 표시는 파일 내용끼리 비교 — 둘 다 base 쪽 변경을 내 변경과 못 가른다.

## 2. 완료 조건

1. S1 → `확인함` 유지(행에 "확인한 변경 그대로" 표시 — diff 는 바뀌었지만 내 변경 블록은 전부 본 것).
2. S2 → `확인함` 유지.
3. S3 → `확인 후 바뀜`, "확인 후 바뀐 곳" 탭에 내 새 블록이 든 덩어리만, dev 줄은 +/− 로 안 보임.
4. dev 와 내가 같은 줄을 다르게 고침(내 + 줄은 같고 − 줄이 바뀜) → `확인 후 바뀜`, 그 블록이 보임.
5. mode·상태·이전 경로가 바뀜 → `확인 후 바뀜`(내용이 같아도).
6. base 가 안 움직인 평소 흐름(커밋만 쌓임) → 지금처럼 `확인 당시 blob → 지금 blob` 의 바뀐 줄만.
7. 이 기능 전에 쓴 기록(새 필드 없음) → 지금 동작 그대로.
8. 기존 core·web·desktop 테스트 통과.

## 3. 정의

- **블록**: base...head patch 의 한 덩어리(hunk) 안에서 연속한 `-`/`+` 줄의 최대 묶음. 문맥 줄(` `)과 덩어리 머리(`@@`)는 안 든다. `\ No newline at end of file` 줄은 바로 앞 줄이 `-`/`+` 면 그 블록에 붙이고, 문맥 뒤면 버린다(끝 개행 변경도 내 변경이다).
  - 덩어리가 아니라 블록 단위인 이유: dev 가 내 두 변경 사이에 줄을 넣으면 -U3 덩어리가 갈라지거나 합쳐진다. 블록은 문맥과 무관하다.
- **서명**: `HMAC-SHA256(secret, JSON.stringify([앞 문맥, ...블록 줄, 뒤 문맥]))` 앞 16 hex. 앞/뒤 문맥 = 블록 바로 앞·뒤 줄이 문맥 줄(` `)이면 그 줄, 아니면(덩어리 처음·끝) `''`. (2026-10-19 리뷰 반영 — 같은 `-/+` 블록이 다른 위치에 나타나는 것과 구분. 3줄 전부가 아니라 1줄인 이유: dev 가 2줄 떨어진 곳을 고친 S1 이 계속 맞아야 한다) secret 은 기록 키와 같은 것(gist 모드 = 공유 비밀, 기기 모드 = 고정값) — 짧은 줄(`+}`)의 해시가 사전 공격으로 풀리지 않게. 줄은 정규화하지 않는다(공백·CR 변경도 변경이다).
- **meta**: `sha256(JSON.stringify([status, previousPath ?? '', mode ?? '']))` 앞 16 hex.

## 4. 데이터

- `Snapshot.mergeBase?: string` 추가. 로컬 = `loadLocalSnapshot` 이 이미 구하는 `mb`. GitHub = compare 응답의 `merge_base_commit.sha`(이미 받는 응답, 추가 요청 없음).
- `ViewRecord` 에 선택 필드 3개: `blocks?: string[]`(patch 순서의 서명) · `base?: string`(확인 당시 merge-base) · `meta?: string`. 체크할 때 함께 쓴다. 코드 내용은 여전히 gist 에 안 간다(서명·커밋 해시만).
- `sync.ts assertState`: 세 필드가 있으면 타입을 검사(blocks = 16 hex 문자열 배열, base = 40/64 hex, meta = 16 hex), 없으면 통과. 옛 앱(폰 PWA 캐시)은 필수 필드만 보므로 새 기록을 읽어도 깨지지 않는다.
- 자동 기록 없음: 판정이 바뀌어도 기록을 쓰지 않는다. 사용자가 체크·해제할 때만 쓴다.

## 5. 판정 (`buildReview`)

```
record 없음 / viewed=false        → unread
record.fp == fp                   → viewed                         (지금과 같음)
record.blocks 없음(옛 기록)       → changed-since-viewed           (지금과 같음)
file.patch 없음(바이너리·종류 변경·서브모듈·너무 큼) → changed-since-viewed
record.meta != meta               → changed-since-viewed
record.base 또는 snap.mergeBase 없음, 또는 둘이 같음(base 안 움직임) → changed-since-viewed
                                  (base 가 그대로면 지문 변화는 전부 내 변경이다 — 블록으로 거를 소음이 없다)
지금 블록 서명 vs record.blocks 를 최장 공통 부분열로 맞대(core 에 직접 구현 — 앞뒤 공통 블록을 잘라 낸 가운데만 표로, 가운데가 100만 칸을 넘으면 가운데 전부 안 맞음)
  안 맞은 지금 블록 0개           → viewed, carried = 'same'(확인한 블록이 전부 남음, S1) 또는 'shrunk'(일부가 diff 에서 사라짐, S2)
  1개 이상                        → changed-since-viewed, newBlocks=[안 맞은 블록 번호]  (S3·겹침)
```

- 순서를 지키는 부분열 매칭: 블록 순서를 바꾼 것은 변경으로 잡는다. 같은 블록을 한 번 더 넣으면 두 번째는 안 맞는다.
- 진행률·"전부 봤다"·"확인한 파일 숨기기"·체크박스는 전부 이 `state` 를 본다 — 판정이 한 곳이라 어긋날 자리가 없다(cursor 지적).

## 6. 표시 (`SinceViewed`, `changed-since-viewed` 일 때)

- `record.base` 와 `snap.mergeBase` 가 같다(base 안 움직임) → 지금처럼 `확인 당시 blob → 지금 blob` (줄 단위로 정확, base 변경이 끼어들 수 없음).
- 다르다(리베이스·머지) 그리고 `newBlocks` 가 있다 → **지금 patch 에서 새 블록이 든 덩어리만** 보인다. base...head patch 라 dev 줄은 +/− 로 나올 수 없다. 탭은 지금처럼 "확인 후 바뀐 곳" / "전체".
- 그 밖(옛 기록 등) → 지금 동작.
- `carried: 'same'` 배지 "확인한 변경 그대로"(en "Reviewed changes unchanged", 중립색). `carried: 'shrunk'` 배지 "확인한 변경 N개가 빠짐"(en "N reviewed changes dropped", 경고색) — base 에 들어간 것(S2)과 리베이스·머지 중 빠진 것을 서명만으로는 못 가르므로 확인함으로 두되 신호를 남긴다. G4 의 펼침으로 열면 전체 diff.

## 7. 한계 (알고 받아들임)

- 리베이스 뒤 기존 블록 안을 고치면 그 블록이 든 덩어리 전체가 보인다(줄 단위 아님). Jell 이 감수하기로 함(3-way 정밀 비교는 스파이크로 8/8 검증해 둠 — 나중에 표시에만 얹을 수 있다).
- `carried` 로 확인함이 된 파일은 기록이 그대로라, 그 뒤 커밋은 base 가 다르게 보여 덩어리 단위로 보인다(다시 체크하면 기록이 새로 써져 줄 단위로 돌아간다).
- 옛 기록은 다시 체크할 때까지 지금 동작.
- base 가 움직인 상태에서 확인한 블록이 사라지면(스쿼시 흡수든 리베이스 중 유실이든) `확인함` + "N개가 빠짐" 배지 — 서명만으론 둘을 못 가른다. base 가 그대로면 블록이 사라진 것도 `확인 후 바뀜`.
- 리베이스 중 앞뒤 문맥 줄까지 똑같은 블록이 다른 위치에 생기면 여전히 확인함으로 맞춰진다(복사된 코드 덩어리) — 줄 범위 3-way 만 막는다.
- base 가 내 두 블록 사이 문맥 줄을 지우면 두 블록이 하나로 합쳐져 `확인 후 바뀜`(보여 주는 쪽이라 안전한 방향의 소음).
- 블록 비교는 앞뒤 공통 블록을 잘라 낸 가운데만 표로 계산하고, 가운데가 상한(100만 칸)을 넘으면 가운데 블록을 전부 안 맞음으로 본다.

## 8. 기각한 대안

- 덩어리별 `applyPatch` + `reversePatch` 로 확인 당시 파일을 새 base 로 옮기기(초안): jsdiff 가 fuzz 0 에서도 위치를 옮겨 찾아 **중복 블록에 잘못 적용 → 진짜 새 변경을 확인함으로 숨김**(codex 재현, 스파이크 8개 중 4개 틀림 — 그중 2개가 숨김).
- 줄 범위 3-way(확인 당시 파일을 base 변경과 합쳐 지금 파일과 비교): 스파이크 8/8 이지만 base 시점 파일 읽기(새 git 명령·GitHub 바뀐 파일당 ~4요청)와 확인 당시 커밋 보존이 필요 — Jell 이 블록 서명을 택함.
- `merge-base(record.head, 지금 base)` 로 확인 당시 기준 추정: base 교체·dev force-push·머지 흐름에서 틀린다(codex) → 확인할 때 `base` 를 기록.
